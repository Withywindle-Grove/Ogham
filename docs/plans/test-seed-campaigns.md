# Plan: seeded test campaigns for each setting (tester, 2026-11-03)

Francis ruled A (2026-11-03): a script that builds, on the **test** project only, one or two campaigns per setting with a character for every class (every kindred or race covered), rebuildable before each gate. Uses: the full character sheet review (designer), the options audit's checks, and each milestone gate.

## What this step delivers
`npm run seed:test` (and `-- --reset`) runs `scripts/seed-test-campaigns.mjs` on Francis's PC:
1. **Refuses anything but the test project** (checks the project ref against the test one, as `db-push-test.mjs` does; any doubt, stop).
2. **Reads the newest private packs** from `packs/_current/` at run time (fae-woodland, classic-advanced, the zine overlay, deathcaster-class; whatever settings are present). The script and its tests hold **no pack content**: no names, rules or numbers (hard rule 2); everything comes from the files.
3. **Signs in as a dedicated test GM** and two test players (accounts on the test project; credentials from a local, gitignored env file, never committed), imports the packs into the GM's library (Update when present).
4. **Creates the campaigns**, named "Seed · <pack's own name> · defaults" and "Seed · … · options on" (the second switches on the options that add creation steps or fields; the list comes from the options audit once it exists, until then every option whose `byOption` or `option` gates a creation step).
5. **Creates characters through the app's own creation commands** (the same path as the guided flow's Send; hard rule 3: commands, `can()`, events), one per class, rotating kindreds or races so each appears at least once, plus kindred-classes in the options-on campaign. Values are fixed and typical (scores at the dice average adjusted to meet the class, hit points at the die's average, the first kit, the first row of each roll, first spells from the first table row): test data, not dice (the app's never-rolls rule is about the app). The GM approves them; half are owned by each test player.
6. **`--reset`** removes only the campaigns whose names start with "Seed ·" on the test project (through the app's own retire / delete commands where they exist; a direct delete of test-only seed rows is acceptable here and named in the script), then rebuilds.
7. **Prints a summary**: campaigns, characters per class and kindred, anything skipped and why (a class the creation commands refused, with the refusal).

## Rests on
The creation commands as built (m5b-0c). If a class can't be created through them, that's a finding for Francis, not a workaround.

## Tests (purpose first)
- The script stops when pointed at anything but the test project.
- With an invented fixture pack (`scripts/fixtures/m5b-creation.fixture.json`), a dry run plans one character per class and covers every race.
- `--reset` touches only "Seed ·" campaigns.
- No string from a real pack appears in the script or its tests (check-names hook).

## Scope checks (write one and stop)
- Creating characters any way other than the app's creation commands.
- Any new migration, RPC or permission to make seeding possible.
- Anything that would run against the main project.

## Manual checks (add to docs/testing.md)
- Run `npm run seed:test`; sign in to the preview as the test GM: the seed campaigns are there, each class has a character, every kindred or race appears, each sheet opens.
- Run it again with `-- --reset`: the same campaigns, rebuilt; nothing else in the test project changed.

## Estimate
About 4–6 tester turns. Francis runs it on his PC (it needs `packs/`), about two minutes a run.

## Departures

**Designer, 2026-11-03 (`design/rulings/m5b-seed-input-2026-11-03.md`):** si-1 covered by of-2 (nothing to change in the seed). si-3: in shop campaigns, buy through the shop commands within the starting money: the cheapest armour and shield the class may use, one weapon it may use, a backpack, a week of rations, a light source; then wear and hold them (about 1 turn). Changes to individual seeded characters come from the designer as notes (what, which campaign, which class).
(The tester keeps this current.)

1. **Built and tested without a live run.** The worktree has no `.env.test`, `.env.seed` or `packs/`, so the script was run only as a dry run on the invented fixture and through its unit tests. The first real run on Francis's PC is the real test (manual checks in docs/testing.md).
2. **No scope check needed.** Seeding uses only existing commands: `campaign.create`, `library.import` / `library.update`, `rules.attach`, `field.useLayout`, `invite.create` / `invite.redeem`, `character.create` (as a draft), `character.send`, `character.review`. No migration, RPC, permission or route was added. The script imports the app's own `.ts` modules directly (Node 24 reads them).
3. **Follow-up (PR after #349, Francis 2026-11-03): kit, first spells, first trait entries, languages.** Written as the owner before the character is sent, with `inventory.add`, `character.edit` (fields and the creation record) and `creation.spellBook.set`, planned by the app's own pure rules (`languagesPlan`, `firstSpellsPlan`, `traitSteps`, `kitTaken` …) from the campaign's setting as the player's screens load it (`loadCampaignSetting`). The kit is the class's first, taking row 1 of each roll; the record keeps `bought`, `givenGear`, `traitGear`, `spentBase` and `gearDone` as the Gear step does. Francis added two more (2026-11-03): after the character is made, the kit's first armour and first shield are worn and its first weapon is held through `inventory.equip` (the Pack's Put it; `scripts/seed-equip.mjs`), and weapon skills are set through `character.edit` wherever the weapon-skills step exists (its option is on, so the "options on" campaigns), taking the first weapons the step offers up to the level's picks.
3a. **Departures of the follow-up:** (a) `copyOf` and `bundleOf` are copied from `src/app/AddItem.tsx` into `scripts/seed-extras.mjs`, and the equip checks (`equipCheckWith`, `loadEquipContext`) from `src/app/EquipWarning.tsx` into `scripts/seed-equip.mjs`, because those files are React and Node cannot load them; the rules they call (`equipBlocks`, `equipWarnings`, `scoresOf`, `weaponSetup`) and the commands are the app's own. (b) Kit things are added to the pack carried (inside the kit's backpack when it has one), then put on in a second step after the sheet and pack are final: the first armour, the first shield, the first weapon that fits the free hands (never a stack). The class's rule or the setting's warning is checked first, as the Pack does; a blocked or warned item is **reported, not forced** ("Do it anyway" is never used), so AC may stay bare for a class the kit does not suit. `wearKit` is covered only by a live run (its pure parts are tested). (c) The starting money on the record is the money roll's typical total (at least the kit's price); no money roll is logged, so the log has no "rolled" line for it. (d) A language list that lets any be picked ("pick any your GM allows") gets only the given languages. (e) A table a player cannot read is skipped and listed under "left out". (f) Like the rest of the script, this has been run only on the invented fixture (planner tests), not against the live test project.
4. **`--reset` deletes with the test project's service key**, not through an app command (the app has no "delete campaign"). It selects names starting with "Seed ·" and deletes only those ids; a test checks this. Whether the database cascades cleanly (events, characters) is **not verified**; if a delete is refused, the script stops and says which campaign.
5. **Options on = the options other entries depend on** (`option`, `onlyWithOption`, `byOption`), each switched to the choice an entry names, else the first non-default one; the creation-method option stays at its default. This is the plan's stop-gap until the options audit exists.
6. **Overlays and creation methods (after the first real run, Francis 2026-11-03).** The first run seeded overlays on their own, so their classes all said "Needs CON 9" (no scores without the base). Now a pack with classes is seeded on the packs its `meta.requires` names, the base first, merged the way the app stacks them (one entry per kind and id, the higher pack winning, then each class's `raceMaxLevels` widening the races as the app does); it is still seeded on its own as well. A pack with no classes of its own (an adventure) is skipped even when it requires a base. Each creation method the default doesn't offer (a choice with no `methods` list of its own) gets one more campaign with that method chosen, so race-as-class characters exist. **Stack order is the order `requires` lists the bases** (a conversion listing two settings gets the first lowest); say if one should be the other way round. More campaigns means a longer run (about 10–20 minutes). **Shop campaigns (si-3, ruled 2026-11-03):** where a class has no kit and the setting has a shop, the seed buys a starting set (`shopSet` in `scripts/seed-extras.mjs`). Items are found by their data (slot, weapon, container, light) and by plain words in their names ("backpack", "ration", "lantern", "torch", "candle", "lamp"), never by a pack's names; a pack that names them differently gets a "no … was found" line. A ration item whose name or text says it lasts a week (or 7 days) is bought once, otherwise seven. "Through the app's shop commands" is `inventory.add` with `howGot: bought` and the cost, exactly as the shop does it; the purchases go on the creation record like the Gear step's, and `forSale` is copied from `AddItem.tsx` (React) as `copyOf` was. **Summary tidy (second real run):** a class one method doesn't offer isn't listed as left out when another campaign of the same setting makes it; kindreds aren't listed as uncovered when no method has a kindred step; a pack with no ability scores in its rules (a homebrew that is only a table of items) is not seeded on its own, only on top of a setting.
7. **Campaign settings are the database's defaults** (no encumbrance or time choices), except what a sheet layout sets (hit points asked).
