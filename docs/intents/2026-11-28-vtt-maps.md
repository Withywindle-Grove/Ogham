# Intent: virtual-tabletop maps (.vtt)

Author: Francis · Date: 2026-11-28 · Status: draft (for the build loop's step 1, the design sitting)

## Problem
A new roadmap item. Francis, 28 Nov 2026:

> "another item for our roadmap - integration with .vtt files"

Asked which kind, he answered: "virtual-tabletop maps (A)". These are the Universal VTT map files (`.uvtt`, `.dd2vtt`, `.df2vtt`), not WebVTT captions.

## Outcome
Not decided. The sitting says what "integration" means for the app's maps.

## Context (from the Pack Creator, 28 Nov; facts, not rulings)
- His own example was a plain black-and-white dungeon picture named `.vtt`: a picture ready for a virtual tabletop, with no wall data.
- A true Universal VTT file is JSON: the picture, the grid, sight-blocking walls, doors and lights.
- The pack format gives a map its picture and key points only (`pins` reserved; `07-content-packs.md`). Walls, doors or a grid are a format gap, and need a design ruling first (G-235, `11-modelling-gaps.md`).

## Touches
Pack format for maps (07), the map screens (06, 05), the data model (04) if walls or a grid are stored. Gap row G-235.

## Constraints
- Mockups first (CLAUDE.md): nothing visible is built before he approves a picture.
- Hard rule 2 applies: no game IP in examples or tests; invented maps only.
- Hard rule 9: reading or writing the file may need a dependency; ask first.

## Out of scope
Nothing is decided beyond his words: no ruling, no release, no format change.

## Open questions
- ⚑ What does the app need from a dungeon map: the picture with room keys, as today, or walls and doors too?
- ⚑ Import into the app, export from it, or both?
- ⚑ Release: Francis to choose (R1 before table test 1, or R2/R3).
