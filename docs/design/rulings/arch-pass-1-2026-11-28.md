# Architecture pass 1: rulings (2026-11-28)

## Candidate 1: one module for "Undo my last change"

**Verdict: yes, through the loop.** Intent: `docs/intents/2026-11-28-arch-undo-module.md`.

What the code shows (searched 28 Nov at `bf1c09c`): 29 files outside `src/core/undo.ts` call `latestChange`, 37 times. Each call finds the person's newest change of a kind, runs `undoChange`, picks the words and refreshes. `latestChange` answers null both when there is no such change and when the read failed, so a failed read shows "Nothing to undo."

| Id | Ruling | What it means | Francis |
|---|---|---|---|
| arch1-1 | **Build the module, through the loop** | One module in core does "undo my last change of this kind" and reports one of three endings: undone, nothing to undo, could not check. Each screen keeps its own words and its own refresh. One small spec, about three tickets. No stored data changes | "A" |
| arch1-2 | **The refactor keeps today's words** | A failed read still shows what each screen shows today, so no screen changes and the spec is "data and logic only". The module reports "could not check" to the screen all the same. The new words for that ending are one ⚑ for the next design sitting (`docs/10-open-questions.md`); one small ticket changes them after he rules | "A" |
| arch1-3 | **Candidate 1 does not wait for candidate 3** | The module makes its own small three-way answer for this one read. If candidate 3 is a yes, it takes that answer over and makes it general | "A" |

Technical decisions, Claude's (Technical ownership), put to Francis with Q3; he did not object:

| Id | Decision | Why |
|---|---|---|
| arch1-4 | The module lives in `src/core/undo.ts`. It finds the change, runs the undo and reports the ending. The screen shows the toast and refreshes. The log's own Undo (on a log line) is out of scope. The module gets its own tests for the three endings; the screens' tests that tap a toast's Undo stay and must pass unchanged; no test is deleted | The undo rules are already in that file. A screen's words and refresh are its own. A log line already knows which change to undo |

Found while checking, for the builder: the callers do not all say the same thing. 22 show "Nothing to undo.", 5 answer "There was nothing to undo.", and one already shows "Couldn't undo that. Check your connection and try again." Under arch1-2 each keeps its own words.

## Candidate 2: log wording lives with its module, not in core

**Verdict: yes, now, as a trial first.** Intent: `docs/intents/2026-11-28-arch-log-wording.md`.

What the code shows (searched 28 Nov at `bf1c09c`): `src/core/events.ts` has 1,985 lines; `describeEntry` (line 603) writes every log sentence, in 205 cases. Core never imports a module (hard rule 6, `02-architecture.md`, Foundation 5), so core re-types what modules know (line 539 says so). The file changed in 21 commits in four weeks. The tests call `describeEntry` 28 times, so most of the 205 sentences have no test of their words.

| Id | Ruling | What it means | Francis |
|---|---|---|---|
| arch1-5 | **Move each module's log sentences to that module, now** | A module gives the registry the sentence for each of its commands. Core still loads and groups the log and asks the registry for the sentence. Every sentence comes out word for word the same. It does not wait for 5 December (the lean was "after"; he chose now) | "B" |
| arch1-6 | **A trial first, then the rest** | Spec 1 has three tickets: the safety net, the registry's new slot with core's old path kept as fallback, and one small module moved (requests). From its merge a new command writes its sentence in its own module. The other modules follow as a second spec, after 5 December or on his word | "A" |

Technical decisions, Claude's (Technical ownership), told to Francis with Q2:

| Id | Decision | Why |
|---|---|---|
| arch1-7 | Ticket 1 is a safety net: a test that records one real sentence for each of the 205 cases, before any sentence moves; every later ticket leaves the record unchanged. The slot is on the command registry (`src/core/commands.ts`), which every module already registers with. The trial module is requests (7 cases). Core's `describeEntry` stays as the fallback for a command with no registered sentence until the second spec's last ticket | Only 28 of the sentences are tested today, so "word for word" could not be proved. Requests is small and its sentences use core's shared names, so it tries the slot's shape |
